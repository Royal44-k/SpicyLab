# 食材搜索、库存满足、排序与采购

## 先分清四个问题

1. **用户可能想找什么？** 查询召回可以较宽。
2. **家里是否有这道菜需要的具体材料？** 满足判断要严格。
3. **手上的材料可否替代？** 需要工艺、形态、风味、过敏与用户接受条件。
4. **数量是否足够做指定份数？** 需要数量、单位、可食率及消耗计划。

不得用一个“相似度百分比”同时回答四件事。UI优先显示“主料已匹配；还缺鱼头”“可换做鱼片版”这类具体解释。

## 分层数据模型

```text
IngredientConcept: id, preferredName, aliases, familyIds
IngredientVariant: conceptId, species, cut, state, preparation, edibleYield
PantryLot: variantId, quantity|null, unit|null, acquiredAt?, storage?, confidence
RecipeRequirement: variant/constraints, role, required, quantity, unit, acceptableSubstitutions
MatchExplanation: relation, satisfied, quantityStatus, matchedPantryLot, reasons, missing
```

名称标准化只处理空格、明确同义词、常用书写差异，不丢掉决定工艺的部位/形态。`干红辣椒→干辣椒`可按词典归一；`老豆腐→嫩豆腐`不能普遍等价；`鸡腿→去骨鸡腿肉`需要处理步骤和净料换算。

| 关系 | 示例 | 可召回 | 自动抵扣 |
|---|---|---|---|
| 精确/严格同义 | 干红辣椒→干辣椒 | 是 | 条件与数量满足时 |
| 具体满足泛化 | 符合工艺的牛里脊→炒牛肉所需牛肉 | 是 | 经部位/状态约束确认时 |
| 同族相关 | 鱼肉→花鲢鱼头 | 是 | 否 |
| 显式替代 | 去皮鸡腿肉用于指定家常鸡丁变体 | 是 | 用户接受且变体有效时 |
| 文字巧合/不相关 | 鱼→鱼香肉丝、肉→木耳 | 否 | 否 |

“具体满足泛化”不是全族通行证：辣椒油不满足切丝青椒，蒸肉米粉不满足米粉条；不能通过传递闭包把互不兼容形态连成等价词。

## 查询流水线

```text
文本输入与中文组合输入结束
→ 规范分隔/别名，保留原词供解释
→ 识别菜名、食材、工艺、菜系、设备和时间意图
→ 应用用户明确的硬约束
→ 精确字段 + 别名 + 受控品类召回
→ 多条件组合
→ 库存与数量判定
→ 稳定排序和理由
```

明确菜名“鱼香肉丝”仍应找到该菜；单独食材“鱼”不靠该菜名字中的字命中。短词“肉”过宽时建议选择猪/牛/鸡等，不返回大量0%伪匹配。未知食材可保留并提示未识别，不能静默删除。

小型结构化库（如36道）用规范化索引、Set/Map和受控词典即可；规模大后再考虑倒排索引、拼写纠正与向量召回。向量候选仍须通过相同硬约束与库存判断，不能让生成模型直接宣布食材齐全。

## 稳定排序

建议按产品模式选择排序：

- 菜名搜索：查询相关度优先，再用库存与时间作次级排序。
- 库存找菜：过滤零相关；先考虑满足程度、主料覆盖、关键缺料，再考虑口味与时间。
- 明确“只看可直接做”：按定义过滤，不混入“换购可做”。

SpicyLab现有顺序是：有查询时先比较查询分 → 可做标记 → 主料满足 → 主料相关 → 加权匹配率 → 缺主料数 → 缺料数 → 时间 → 原目录顺序。该标记只覆盖主料/配菜，升级时先改口径再调权重。

可以给主料3、配菜1的内部权重作为起点，不把它当行业标准。调味料可能是菜的身份关键，不能永远忽略。归一化覆盖率用于排序，不等于实际完成率；用户未录入份量时提示量未核对。

最后使用稳定recipeId或固定目录序，避免重复输入后顺序跳变。记录排序版本和决策解释，有依据时调整，不能针对单道案例硬编码第一名。

## 必测语义集

| 输入与条件 | 应发生 | 不应发生 |
|---|---|---|
| 鱼肉 | 召回剁椒鱼头/鱼片菜，说明缺具体部位 | 宣称已有鱼头 |
| 鱼香肉丝（完整菜名） | 命中该菜 | 因没有鱼肉而过滤菜名 |
| 鱼（食材意图） | 实际鱼类菜 | 仅凭菜名字命中鱼香肉丝 |
| 鸡肉 / 鸡杂 | 相关但区分肉与内脏 | 鸡胸直接抵扣鸡胗 |
| 猪肉 / 腊肉 / 酸肉 | 召回解释各加工状态 | 鲜肉自动满足腌制品 |
| 嫩豆腐 / 内酯豆腐 | 依据具体菜的质地要求 | 一律代替煎老豆腐 |
| 米粉 | 消歧粉条与粉末 | 蒸肉粉自动满足南昌拌粉 |
| 辣椒油 / 青椒 / 剁椒 | 同族相关但功能不同 | 酱油状油料替代蔬菜体积 |
| 鱼肉 蒸菜 | 同时满足两个条件 | 偷偷变成OR并无提示 |
| 只有盐或未识别词 | 空态或调料相关专组 | “主料齐全”推荐 |
| 花生过敏 | 包括复合调料检查 | 只剔除菜名含花生的菜 |

评价集合包含正例、反例、含糊词、别名、口语、多条件和特殊约束。测recall@k与precision@k时维护人工相关性标注；可做误报率单独统计，安全/禁忌漏拦单独设门槛。

## 采购与计划模型

规范键至少包含材料身份、加工状态、可换算单位族。克与千克可精确换算，毫升与克需已知密度，个与克需单重/净料证据；没有依据分行显示。不要把米酒、料酒、醪糟当同一物品合并。

把采购单表示为每个计划实例的贡献：`planItemId + recipeVersion + servings + adaptationVersion → requirements`。同一事件重试使用相同ID不增加量；用户明确做第二次则创建第二个实例。同菜改2人到4人，用新贡献替换旧贡献，不额外叠加，也不因菜谱ID相同而忽略。

`缺量=max(需求量−可用库存分配量−已购可用量,0)`。一份库存不能在多道计划中重复抵扣。已购量与需求量分离，新增需求后重新判定是否全部购齐。撤销某计划只移除其贡献，保留其他计划。普通内容原型无数量时只提供名称级核对，并清楚说明。

## 反馈和改进

用户能指出“不相关/我没有这个部位/替代不合适”。记录原词、规则版本、上下文和错误原因，经编辑审查更新词典。不要直接把一次用户修正扩展成全局别名；保留旧版本并跑完整反例集。
